# Gatekeeper integration handoff

This directory is a native crate plus a React review surface. Lumen connects it
for Claude through `src-tauri/src/approvals.rs` and for Codex through
`src-tauri/src/approvals_codex.rs` (`codex app-server`), with the Ask-first access
mode and the chat panel.

## Verified support, 2026-11-06, Windows

- Installed Claude Code: **2.1.314**. Its hidden `--permission-prompt-tool` flag
  was accepted. A real subprocess initialized and discovered `approve` through
  the native MCP bridge. No model turn was submitted.
- Installed Codex: **0.167.0-alpha.3.2**. A real subprocess generated its JSON/TS
  schemas and completed `app-server` initialization. Its generated schema still
  lists `untrusted`, but starting with `approval_policy="untrusted"` actually
  fails. The launch builder uses `on-request`, `read-only`, and the `user`
  reviewer. The second smoke run succeeded with these settings.
- Native fixture and actual local TCP/MCP tests exercise approve, reject,
  cancellation, timeout, concurrent callbacks, changed previews, and recovery.
- Lumen's own Claude turn, 2026-11-06, Windows: one Ask-first turn asked the
  Gatekeeper for a `Write` action, the broker approved it, the file was written
  and the turn finished. The test is `approvals::tests::approved_action_runs_in_a_real_turn`
  (ignored by default; it needs `LUMEN_GATEKEEPER_MCP_EXE` and a signed-in
  `LUMEN_TEST_CLAUDE_CONFIG`). Read-only tools such as `echo` are auto-allowed
  by Claude Code and never reach the approval tool.
- Lumen's own Codex turn, 2026-11-07, Windows, Codex 0.167.0-alpha.3.2: the
  app-server runner received `item/commandExecution/requestApproval` for a file
  write, the broker approved it, the file was written and the turn completed.
  The test is `approvals_codex::tests::approved_codex_action_runs_in_a_real_turn`
  (ignored; needs a signed-in `LUMEN_TEST_CODEX_CONFIG`). That model turn raised
  no file-change callback, which stays covered by fixtures only. The native
  window (clicks, countdown) and macOS/Linux, packaged executable entry points
  and clean installs remain open.

Official sources checked before implementation:

- [Claude CLI reference](https://code.claude.com/docs/en/cli-reference): the MCP
  permission-prompt tool is for headless runs; some tools requiring user
  interaction cannot be approved by this channel.
- [Claude permission evaluation](https://code.claude.com/docs/en/agent-sdk/permissions):
  provider permission rules and modes act before the permission callback.
- [Codex app-server](https://learn.chatgpt.com/docs/app-server): request routing
  uses server JSON-RPC IDs plus thread, turn and item identities. Command/file
  decisions support one-time accept, decline and cancel.
- [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)
  and [security](https://learn.chatgpt.com/docs/agent-approvals-security): explicit
  `untrusted` is retired; `on-request` allows operations inside the sandbox
  without prompting. This module handles protocol approval requests, not every
  provider action. It does not claim to override the provider's own policies.
- [MCP lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle),
  [tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools),
  [cancellation](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation).

## Native ownership and lifecycle

Add a path dependency in **`src-tauri/Cargo.toml`**:

```toml
lumen-gatekeeper = { path = "../src/features/gatekeeper" }
```

Using a dependency avoids copying files or changing Rust module-relative
imports. Construct one long-lived `Gatekeeper::open(app_data.join("gatekeeper.sqlite"),
Duration::from_secs(300))` in the native app state in **`src-tauri/src/lib.rs`**.
Store the journal beside the existing private app database. Its requests may
contain command arguments and proposed file contents; apply the same storage
permissions and data-retention policy as chat messages. Do not put it in the
project repository or renderer localStorage.

Opening reconciles the old journal atomically: pending requests become `stale`;
responses that might have been in flight become `delivery: uncertain`. Existing
historical decisions remain readable. New ownership also prevents an older
in-memory broker for the same journal from sending further approvals. A failed
journal write releases no approval. A corrupt/unsupported journal returns an
error; display unavailable and stop approval-dependent work.

For every new provider process/turn, call `start_session` with the app chat ID,
provider, actual provider thread/session ID, actual turn ID, canonical worktree
directory and verified `Availability`. Retain the returned `Scope` in native
runner state. Its generated `connectionId` is never restored. Use one scope per
live turn; complete/interrupt the prior turn before starting the next one.
Keep the native session owner independent of renderer remounts.

After restart, show `snapshot()` as recovered history. Integrate the recovery
module's process/effect inspection before restarting the provider. An old
approval never resumes a job. A new supported connection must issue a new
permission request, which receives a new host request ID. `uncertain` means a
response may already have been delivered; it does not authorize retrying the
operation. Do not automatically rerun the associated tool.

## Codex runner changes

In **`src-tauri/src/providers.rs`** / **`src-tauri/src/turns.rs`** and the Orchestra
execution path, select a separate Gatekeeper runner. The existing `codex exec`
path cannot service these callbacks. Do not append its `approval_policy=never`
or bypass flags to `support::codex_args()`.

1. Resolve the selected account's actual executable and isolated environment.
   Run version/schema checks and real `initialize`. `support::codex` validates
   those observations; a version number alone does not establish support. Probe
   errors/timeouts must produce `Availability::Unavailable`. Do not start a
   model turn until initialization and approval support pass.
2. Initialize app-server, send `initialized`, then `thread/start` or
   `thread/resume` with the fields from `support::codex_thread_params(cwd)`.
   Reassert policy/reviewer on resume and turns; merge only the approved model,
   effort, input and account settings. Use actual returned thread and turn IDs
   in `start_session`; do not reuse placeholder plan IDs.
3. Read bounded newline-delimited protocol messages separately from stderr.
   Feed `item/started`, `item/fileChange/patchUpdated`, `item/completed`,
   `serverRequest/resolved`, `turn/completed` to `observe_codex`. It returns false
   for unrelated events. Continue passing normal text/usage events through the
   existing renderer pipeline. Terminal text is never an approval source.
4. Dispatch server approval requests to `request_codex(scope, &message)`.
   Immediately drive `PendingReply::wait()` in a task, **without blocking the
   reader**, so cancellation/resolution notifications and concurrent approvals
   keep flowing. Send replies through one bounded writer queue.
5. Immediately before writing a `Delivery`, call `delivery_is_current`. If
   false, discard it. Write its exact `response` once, then call
   `complete_delivery(delivery, success)`. On partial/failed writes, protocol
   errors, waiter errors or journal errors, interrupt/stop the turn and verify
   the provider process. Never reconnect and resend `accept`.
6. On cancellation, transport loss, item-preview invalidation requiring a new
   callback, runner shutdown or provider switch, call `disconnect` and stop or
   interrupt the affected provider. `disconnect` retires approvals; it does not
   prove that a process has exited. Continue the recovery module's process-tree
   checks. An adapter parse error must not fall back to the headless runner.

Implemented Codex cards cover command callbacks and file changes with a complete
item preview. Network requests, stdin/human-command approvals, additional
permissions, persistent `grantRoot`, unavailable one-time decisions, missing or
malformed previews, and unknown protocols remain non-approvable. Reject/cancel
or a protocol error grants nothing. They need dedicated adapters before adding
broader support. Never automatically convert them into a shell approval.

## Claude runner and executable entry point

In **`src-tauri/src/main.rs`**, branch before initializing Tauri if the only
argument is `--lumen-gatekeeper-mcp`; create a Tokio runtime, call
`lumen_gatekeeper::mcp::proxy_stdio()` and exit with nonzero on error. This path
must emit **only protocol JSON to stdout**. Alternatively package the crate's
`lumen-gatekeeper-mcp` helper as a sidecar. Point `ClaudeEndpoint::config` at an
absolute packaged executable path (`embedded=true` for the main executable).
The standalone helper was built and used successfully by the Windows CLI probe.

1. A diagnostic bootstrap can create a temporary session marked available
   solely to host MCP initialization, as in `examples/probe_cli.rs`. It must
   never submit a user/model turn. This is needed because the endpoint must
   exist before the CLI can discover it. After success, discard that diagnostic
   connection. For a real run, create a fresh session/endpoint using the verified
   CLI evidence and still wait for that endpoint's `readiness()` before sending
   user input. Failure means unavailable, stop the child, no fallback runner.
2. Bind `ClaudeEndpoint` to the native scope. Spawn and supervise `.serve()`.
   Create its MCP config, use `support::claude_args`, pass the selected model
   and effort plus the existing isolated account environment. On resume, replace
   `--session-id` with the correct provider resume flag; create a fresh native
   connection scope and MCP endpoint. Do not inherit skip-permission, auto,
   acceptEdits, remote MCP settings or permissive allowed-tool lists.
3. The endpoint is loopback-only and accepts one authenticated stdio helper.
   Its random per-endpoint capability is passed to the helper in the explicit MCP
   config's environment. Keep that ephemeral config out of command logging,
   persisted settings and transcripts; never print full args on spawn errors.
   The token necessarily passes through the Claude child as part of its
   `--mcp-config` argument; this is a local-process trust boundary, not protection
   against the OS user or an already-compromised provider process.
4. The MCP server validates frames, initialization and request identities. A
   call queues a review; the server waits asynchronously for the native broker
   and replies with MCP text containing `{behavior, updatedInput}` or a deny.
   Input comes exclusively from the immutable native request. Cancellation and
   timeout deny; upstream MCP cancellation retires the callback without a reply.
5. Abort the endpoint task and stop the child on cancellation, bridge loss or
   app shutdown. Dropping/aborting the endpoint invalidates pending requests.
   Supervise `.serve()` so an unexpected bridge exit also interrupts the model
   turn. The proxy cannot approve anything by itself.

Supported Claude inputs: `Bash`, `Edit`, `Write`, `Read`, `Glob`, `Grep`,
`WebFetch`, `WebSearch`. Unknown tools (including interactive user questions)
show unavailable and cannot be approved. An Edit preview shows literal old/new
text and `replace_all`; Write shows the complete replacement content. These are
proposed edits, not a claim about the current disk contents. Raw tool input is
always inspectable.

Claude MCP does not attest the effective Bash cwd after earlier `cd` commands.
The UI labels its directory as **session directory**. Its operations require
manual approval; automatic command whitelisting is unavailable for Claude.

## Renderer bridge and GUI wiring

Add narrowly scoped native commands in **`src-tauri/src/lib.rs`** and typed
wrappers in **`src/lib/bridge.ts`** for snapshot/session/rule reads, `decide`,
`add_rule`, `remove_rule`. Check the invoking chat/window owns the session; do
not expose request ingestion, arbitrary wire replies, `start_session`, capability
flags or protocol inputs to the renderer. Renderer decisions carry only
`requestId`, immutable `Scope`, action and optional note, never command/input.
`Decision` rejects unknown top-level fields.

Subscribe to `Gatekeeper::subscribe()` before taking the initial snapshot; relay
events to the owner view. Refresh from the snapshot on broadcast lag. Mount
`GatekeeperPanel` in **`src/App.tsx`**, supplying only the current chat's requests,
sessions and rules. Native `Scope.sessionId` associates them with the chat;
`providerSessionId` is the actual provider thread identity. The component's
identity checks/countdown are usability checks; the native broker remains the
decision authority. Mounting or rehydrating the component sends no decisions.
Clear stale cards only by provider reconciliation, never by optimistic UI approval.

The optional whitelist editor offers four exact Git command recipes. Native
validation repeats those choices, pins provider/session/connection and canonical
session directory, and matches the **entire original command**. Shell wrappers,
extra arguments, separators, redirects, substitutions, newlines and formatting
variants do not match. Unknown protocol fields and special callbacks disable
automatic matches. Rules are explicit, removable, memory-only, and expire on
disconnect. Adding one does not approve the current pending card. This trusts
the chosen repository's Git configuration and provider shell's command
resolution; it is not a general shell parser or a replacement for the sandbox.
